## Corrections

### 0.1.0-alpha.15 (2026-11-26): the stage 2 pilot on `main` (P0 of STAGE2.md)

* **The pilot is on `main`:** Codex's pilot `2f43a27` (built on alpha.12) is merged onto `main` with alpha.14. Direct editing on the page side, the basic toolbar, the title field and the shared undo history (E2 to E5) come from it. The logoff handover of alpha.13 and alpha.14 (`seq` / `seen`) is kept. The merge needed only the version, the plan (the one on `main` stays) and the tests (both sets kept).
* **High, found while bringing the pilot over:** a page-side edit that was still open counted nowhere. This covered a title typed but not confirmed, and an unfinished composition (IME or dead key). Closing, and so also a logoff, with the page otherwise saved closed the editor without a question, and the title was lost; saving left it out. Now `visual.flush()` applies it before every decision about saving, a rescue copy, opening, "Im Browser ansehen" and closing.

### After the merge (2026-11-26)

* The interface test of the rescue copy waited for the dialog to be closed between two queued questions; that moment is short, and the first run of the alpha.14 re-review missed it (timeout, passed on rerun). The tests now wait for the next question by its title (`answerThen` in `tests/ui/ui.test.mjs`). No change to the program.

### 0.1.0-alpha.14 (2026-11-26): a page in another encoding and a logoff

* **High (re-review of alpha.13):** the interface acknowledged a page (`seen`) as soon as it arrived. For a page in another encoding the question about converting it comes first; a refresh of the project list meanwhile reported "no page" with that page already acknowledged, so the core counted no page. After the conversion, typing, and with the later reports held back, a logoff query was allowed without a question (reproduced by Codex). Now a page is acknowledged only once it is taken or refused; while any handover is still being handled, `seen` stays below it.

### 0.1.0-alpha.13 (2026-11-26): the first page of a session and a logoff

* **High (re-review of alpha.12):** the core learned that a page was open only from the interface's report. Between handing over the first page and that report, a logoff query found "no page" and was allowed, also with text typed meanwhile (reproduced by Codex with the reports held back). Now a page counts as open from the moment the core hands it over (`opened` carries a counter `seq`); a report of "no page" counts only once the interface has handled that page (`seen`), whether it took it or not.
* **Low:** cutting a long name for a rescue copy no longer splits a character outside the Basic Multilingual Plane.

### 0.1.0-alpha.12 (2026-11-26): findings of the review of alpha.11

* **High, logoff with a report on its way:** the core took the interface's state from the window queue, so a logoff query could be answered with an older "saved" state (also while a system dialog held the queue). The state now goes to the core at once and says whether a page is open; while a page is open the core always refuses the query first. With everything saved the editor then closes at once; otherwise the question for unsaved text appears. A session that ends without asking (forced logoff) is not handled.
* **High, a close request during another question:** `closeRequest` was dropped while a question was open. It is now kept and answered once the question is done.
* **Medium, questions taking each other's answer:** a question that came in the moment after another was confirmed could take its answer. Questions now wait in a real line, and each reads its own answer when its dialog closes.
* **Medium, a dialog claim that stays:** if a dialog request could not be queued, its claim stayed set. It is now given back with the matching answer.
* **Rescue copy:** only in `%LOCALAPPDATA%\HtmlSchoolEditor\Rettungskopien`, no longer in the temporary folder as a fallback; names cut to 60 characters before date and time; the answer names the page. (The owner expects rescue copies to be rare in practice.) Deleting rescue copies is up to the subject teacher and the system administrator (owner's decision of 2026-11-26); the program and its notice stay as they are.
* Root `README.md` names the current version (B6).
* **Still open from that review:** "Im Browser ansehen" starts the browser (`ShellExecuteW`) and the command line checks its file (`isFile`, `src/win/main.cpp`) on the window thread; a blocked network drive can keep the process alive after the window closed (accepted writes drain); B7 (builds not reproducible); B8 (`target=_blank` gives no hint). On a shared account every pupil of that account can read the rescue copies (deleting is up to the teacher and the system administrator).

### 0.1.0-alpha.11 (2026-11-26): one file dialog, a late page choice, rescue copy

* **B4** (owner's decision: before the merge): one file dialog per window. The core claims a dialog when the request arrives and refuses a second request until the dialog has closed; it sends `dialogDone` after every dialog request, and until then the interface locks "Projektordner öffnen", "Seite öffnen …", "Speichern unter …" and "Bild einfügen". Criterion X-07.
* **A late page choice** (found while reading alpha.10, before the merge): the answer to "Seite öffnen …" is checked on a worker. If another page was opened meanwhile, a late choice of a file outside the project switched the project folder, and `projectChanged` emptied the editor with what was typed into the other page. The core now remembers the latest open request and drops older answers. Criterion F-14; test hook `HSE_TEST_PICK_DELAY_MS`.
* **B3** (owner's decision: before use with pupils' files): while a save has been on its way for 3 s, the top bar offers "Rettungskopie speichern". It writes the text in the editor with its BOM and every line break to a new local file in `%LOCALAPPDATA%\HtmlSchoolEditor\Rettungskopien` on its own worker thread (no project folder, no file worker), shows the path, and leaves the save and the saved state of the page as they are. A question that comes while another one is open now waits for it. Rescue copies are not deleted by the program (SPECIFICATION.md 6). Criterion F-15.

### 0.1.0-alpha.9 (2026-11-26): preview navigation and window lifetime

Program addresses percent-encode UTF-8 path segments. The preview binds its accepted load to a WebView2 navigation ID and a generation. Switching pages or projects finishes pending deferrals with an explicit empty response and discards queued reads for the old load. Every accepted load owns a separate cache. Project and scan generations also govern folder watch notifications and scan results.

Project file work and preview reads use separate bounded pools. Shutdown closes the window's task queue and completes preview deferrals on the window thread. Accepted writes drain. Running reads are asked to cancel and workers are joined after the window closes. The folder watcher follows project switches without a window-thread join and retries after a failure.

The window dispatches bridge messages after the WebView2 callback returns, including the four messages that open native file dialogs. Queued actions wait while a system dialog runs its nested window loop.

### 0.1.0-alpha.8 (2026-11-25): protection of the page view

Codex review, High and Medium: the request filter used the older two-argument form, which does not cover every frame and worker; there was no frame policy; the results of the protecting settings were not checked; a failed response left the request to the engine; the page's unsaved text was served for any method and context; and a page could trigger the "open this page" question without a click. Now: no name resolution in the browser process, the source-aware filter for every request, every protecting setting checked (the page view stays off otherwise), the page view switched off if a request cannot be answered, only `GET`, documents only for the page itself with a Content-Security-Policy, only pictures, styles, fonts and media otherwise, frames never navigate, and only the pupil's clicks offer another page. Rules in [ARCHITECTURE.md](ARCHITECTURE.md#request-filter-security); probes in the table above. **For the owner:** frames in a pupil's page now show nothing in the page view (they still work in the browser); the specification did not say otherwise.

### 0.1.0-alpha.7 (2026-11-25): one project boundary for all reads and writes

Codex review, High: the boundary was lexical only. A junction inside the project folder let the page view serve files from elsewhere (the list skipped it, the page view did not), and the same held for opening, saving, new pages, the picture folder and the classification of files chosen in dialogs; file links were even listed. Now every read checks the resolved path of the open handle and reads through it, every write checks the receiving folder, new folders are created only below a folder inside the project, dialog choices count as inside only if they resolve inside, and the list leaves out all junctions, symbolic links and mount points. The cache is used only after the same check. Rules in [ARCHITECTURE.md](ARCHITECTURE.md#the-page-view-how-relative-addresses-work); new criterion R-10, measured natively (table above).

### 0.1.0-alpha.6 (2026-11-25): two breaks that meet stay two

Found by a review of alpha.5 (reproduced in `breaks.js`): in `a<CR>b<LF>c` with `b` deleted, the lone `CR` came to stand directly before the `LF`; saved, the two bytes are read as one `CRLF`, so after reopening, or after restoring that undo step, a line was missing. Now a lone `CR` is never written directly before an `LF` break: that `LF` is written as `CRLF` (`keepApart` in `ui/js/breaks.js`). The line before keeps its bytes; only the break of the changed line gains a `CR`, which is unavoidable, since no byte sequence means "CR, then LF" as two breaks. New criterion F-10. Tests: `tests/ui/breaks.test.mjs` (the case, and a random-edit test: 2000 files with random breaks and 25 random edits each, every raw text must read back as the same lines; both fail on alpha.5), `tests/ui/ui.test.mjs` "line breaks: two breaks that meet after a deletion are saved as two"; native F-10 in the table above.

### 0.1.0-alpha.5 (2026-11-25): own line breaks for every undo step and every save

Found by a review of alpha.4 (reproduced in Node and in the browser test): deleting a lone `CR` and undoing to an unsaved intermediate state could write `LF`, and a late save confirmation rebuilt the saved state from the text typed meanwhile, so returning to the saved text later gave `LF` instead of the `CR` on disk. Cause: breaks were known only for the text as read and as last saved; everything else was derived by comparing texts. Now the undo history stores raw texts, so every step keeps its own breaks (`ui/js/editor.js`), every save takes the raw text it sends, and its confirmation records exactly that without changing the current state (`ui/js/main.js`; `restore` and `remember` in `ui/js/breaks.js`). "Unsaved" now also means that a line break differs from the file. New criterion F-09; test hook `HSE_TEST_SAVE_DELAY_MS` in the test build. Tests: `tests/ui/breaks.test.mjs` (3 new), `tests/ui/ui.test.mjs` "line breaks: undo to an unsaved step and a late save confirmation keep a lone CR" (fails on alpha.4, passes now); native F-07 to F-09 in the table above.

### 0.1.0-alpha.4 (2026-11-25): line breaks break by break

Owner's decision of 2026-11-25: mixed line endings are kept. Until alpha.3 the interface turned every break into the one most common in the file (and said so in the message line), so a file with mixed `LF`, `CRLF` and `CR` changed on the first save. Now `ui/js/breaks.js` keeps the kind of every break as read and follows each change; the warning is gone. New acceptance criteria F-07 and F-08 (byte comparisons, [ACCEPTANCE.md](ACCEPTANCE.md#files)), both measured natively (table above). Tests: `tests/ui/breaks.test.mjs` (6) and `tests/ui/ui.test.mjs` "line breaks: mixed LF, CRLF and CR are saved byte for byte as they were read".

### 0.1.0-alpha.3 (2026-11-25): lost work, from the final Codex report

* **Open and new-page answers** could arrive in another order, replace text typed after the request, or bring a page of a project folder opened meanwhile. Now every request carries an `op`; the interface takes only the answer to its latest request and locks the code field until it comes; the core answers work of an older project folder with `openFailed`. Picture answers carry the `op` too and are inserted only into the page they were chosen for.
* **Baseline**: the core kept "the content last read or written" per path, so a late reopen could replace it, and a save with no known content wrote anyway. Now the fingerprint travels with the open page (`base`); the core writes only over that content and writes nothing without it.
* **Writing**: `ReplaceFileW` without a backup name loses the old file on some failures, and the temporary file was then deleted as well. Now with a backup name; after a failure the core looks at which file is where, puts the new or else the old content back, and keeps the backup if that fails. A save of a file deleted meanwhile is reported, no longer created. A new page and Save As to a new name use a rename that does not replace (no half-written file under the final name); the way out of a conflict ("Als neue Datei speichern") never replaces a file. Temporary names that are taken are retried. After any failed write the file is read again, so a write a network drive reported wrongly counts, and an uncertain state is said.
* **Size**: a page over 5 MB is no longer saved (interface and core), since the editor could not open it again.
* Details in [ARCHITECTURE.md](ARCHITECTURE.md#messages-between-user-interface-and-core).

Tests: `tests/ui/ui.test.mjs` "opening: only the answer to the latest request is taken; the code field is locked meanwhile", "saving: the base of the open page goes with every save; out of a conflict only a new file", "pictures: an answer for a page that is no longer open is not inserted"; `tests/core/core_tests.cpp` fingerprint text; native checks in the table above.

### 0.1.0-alpha.2 (2026-11-24): the two save answers

* **Close after an older save** (lost work): the answer to the save chosen on closing closed the window even if the pupil had typed on meanwhile. Now the answer is checked again: with new text the question comes again, and the window closes only when everything is saved. A failed save keeps the window open.
* **Answer to the save of another page** (lost work): the late answer of A gave B's text the name of A. Now opening, another folder or closing waits for the save on its way, and every save carries an `id` the core sends back; answers to any other save or page are ignored.

## Known gaps of this first code

* Reload of the page view: every pause in typing reloads the page; it may flicker, and pictures that load late can move the restored scroll position.
* The conflict check reads the file and then replaces it; another program can still write in the moment between (no stronger guarantee without locking the file).
* The notes name a missing file by its place in the project (`bilder/Hund.png`), not by the address as written in the code (`../bilder/Hund.png`).
* Third-party notices: the licence text of the WebView2 SDK is added after the first download (the loader library is linked into the exe).
* No application icon.
