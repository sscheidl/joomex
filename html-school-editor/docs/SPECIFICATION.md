# Specification

Product: an offline HTML learning editor in one file. Audience: pupils of about 12–13 years in a computer-science class, and their teachers. This document states what the product does. The numbered requirements it answers (P-, S-, T-, X- and RF- identifiers) are defined in the task brief: [brief/ACCEPTANCE.md](brief/ACCEPTANCE.md) and [brief/REFERENCE_FINDINGS.md](brief/REFERENCE_FINDINGS.md). How it is built is in [ARCHITECTURE.md](ARCHITECTURE.md); what was measured is in [ACCEPTANCE_RESULTS.md](ACCEPTANCE_RESULTS.md).

## 1. Behaviour

### Start and layout

* The file `school-editor.html` is opened directly from the file system in current Edge or Chrome. It needs no installation, server, network or stored browser data. Firefox is not a target of the task brief; it was measured from version 0.1.0-alpha.3 on and the differences found were corrected in 0.1.0-alpha.4. In Firefox, Save is always a download.
* Left pane: the complete HTML source of the document in an editable text field with line numbers and syntax colours. Right pane: the page, directly editable. Both panes are always visible; the divider can be dragged.
* A new page starts from a small German template with doctype, `lang`, charset, title, one heading and one paragraph.

### Editing

* Typing in the source updates the page after a short pause, at the latest before the page can be edited.
* Typing in the page updates the source after a short pause, at the latest before the source is used for anything (saving, formatting, undo, typing in the source, opening another file).
* Toolbar for the page: paragraph, heading 1–3, bold, italic, underline, superscript, subscript, highlight, bulleted list, numbered list, alignment (left, centre, right, justified), link, remove link, image. Buttons that belong together stand close in a group; groups are separated by a line, in the top bar as well. Commands act on the selection of the page; the selection survives the click on the button. A click on an image selects it.
* Markup written by the editor: `<p>`, `<h1>`–`<h3>`, `<b>`, `<i>`, `<u>`, `<sup>`, `<sub>`, `<mark>`, `<ul>`, `<ol>`, `<li>`, `<a href target>`, `<img src alt width>`, `<br>`, and the text of `<title>`. Bold and italic use the basic tags `<b>` and `<i>` because they match the labels of the buttons (confirmed by the owner on 2026-11-19); existing `<strong>` and `<em>` are recognised and removed by the same buttons. The editor never writes `<span>` or `<font>`. The one style attribute it writes is `style="text-align: …"` for the alignment buttons, because HTML has no tag for alignment.
* Underline, superscript, subscript and highlight work like bold and italic (from 0.1.0-alpha.5, owner's request): on the selection or the word at the caret, again to remove. Superscript and subscript exclude each other: one takes the other away from the text it is given to. Ctrl+U underlines.
* New block elements are written on their own line, indented like their neighbours.
* Pasting inserts plain text only. Dropping content into the page is not possible; dropping a file on the window opens it (HTML) or offers to insert it (image).
* Links: the address is checked. Allowed are `http:`, `https:`, `mailto:`, `tel:` and addresses without a scheme (other pages of the pupil, anchors). Everything else is refused with an explanation. With the caret or the selection inside one link, the link button opens the dialog with the address of that link and changes it. A clicked picture can be made a link the same way. A check box "In neuem Tab öffnen" writes `target="_blank"` (no `rel`); for an existing link it shows whether its target is `_blank`, read from the source, and changing it rewrites only this attribute. Unticking removes a target only if it is `_blank`.
* Images: only after choosing a file. PNG, JPEG, GIF and WebP are accepted by their file signature. The source gets the file name as address, with an optional folder in front (`<img src="bilder/katze.jpg" alt="">`); the picture is not copied into the document. The dialog looks for the file at the address it will write and says "Gefunden" or "Nicht gefunden"; if it is not there, the pupil is told where to put it. The characters `#`, `?` and `%` of a file name are written as percent codes so that the address still means this file. A description (alternative text) and a width in pixels are optional; without a description the editor writes `alt=""`. With an image selected, the image button opens the dialog with the values of that image: description, width, folder, and another file can be chosen. A new width removes a `height` attribute so that the picture keeps its proportions. Decisions of the owner of 2026-11-19: file names instead of embedded data, and the description optional.
* The browser does not tell the editor from which folder a file was chosen. The folder part of the address therefore comes from the folder field alone: choosing the same file name again from another folder changes nothing in the code unless the field is changed. Below the field the dialog shows the address that will stand in the code, and it updates while the pupil types.
* Showing images (decision of the owner of 2026-11-19, from 0.1.0-alpha.4): the editor lies in the folder of the pupil's pages, so a plain relative address (with or without folder, also `../`) means the same file from the editor and from the page. The page pane shows that file. It works only if the opened page lies in the same folder as the editor; the editor cannot tell where a page was opened from, and this condition is stated in the help and the guide. A file that is not there becomes a box with the text "Bild nicht gefunden: …", and a note above the page lists the missing addresses (not the note about switched-off content). The editor looks again when the pupil comes back to the editor window from another program, when another document is opened and after the image dialog; never by itself. Pictures embedded in the code (`data:` address) are shown as before. Pictures from the network and from other computers are never shown; their box says "Bild aus dem Internet", and its tooltip asks the pupil to download the picture, mind the copyright, put it into the folder and link it by its file name.
* Alignment: the four buttons set `text-align` on the paragraphs, headings, list items or table cells of the selection, or on the block around a selected image (an image that stands directly in the page gets a paragraph of its own). "Left" removes the declaration; if a rule of the page would then align the block differently, `text-align: left` is written out. An existing `style` attribute is read as CSS, with its strings, comments, escapes and brackets: only a real `text-align` declaration is replaced, every other declaration stays as written. If the text cannot be split into declarations with certainty (a string, comment or bracket is left open), the attribute is left alone and the pupil is told to change it in the code.
* Page title (from 0.1.0-alpha.5): a field above the page pane shows the title of the page and changes the text of `<title>` in the source when the pupil presses Enter or leaves the field. A page without a title gets one new line with a title element at the start of the head. It is the one edit of the head; the editor checks with the browser's parser that the page then has exactly this title and an unchanged body, and refuses otherwise with a message.
* "Im Browser öffnen" (from 0.1.0-alpha.5): opens the saved page in a new tab as a real page, addressed by its file name next to the editor, without a connection back (`noopener`). There its scripts run and its links work; pupils test their links there. A page with unsaved changes or one that was never saved is saved first, after a question. If the saved copy went to "Downloads", nothing is opened and the pupil is told where the file is. If the page does not lie in the folder of the editor, the tab shows "file not found"; the status line says what that means.
* Dialogs can be moved by their heading (the two question dialogs without heading by their text), never out of the window; the next time they open centred.
* The top bar shows the version next to the name, and the save state in bold: "● nicht gespeichert" in a warning colour, "gespeichert" in green.
* Undo and redo: one history for both panes and the toolbar. Continuous typing in one pane is one step until a pause of one second or after four seconds. Opening or creating a document starts a new history.
* "Code aufräumen" (format): one block element per line, two spaces per level, inline content on one line, a line break after `<br>`. Only white space changes. The content of `pre`, `textarea`, `script`, `style`, `svg`, `select` and similar elements is not touched. The style rules of the document (style elements and style attributes) are read as CSS, and the result is applied only if all of this holds: (1) no rule can make spaces count (any `white-space` or `white-space-collapse` value other than the collapsing ones, under any condition); (2) no rule that holds only sometimes changes the kind of box (`display`, `all`), generated content (`content`) or a custom property, and no such property takes its value from a custom property; "only sometimes" means inside `@media`, `@supports`, `@container`, `@keyframes` and every other conditional at-rule, or behind a selector that depends on a state such as `:hover`, `:focus`, `:target`, `:checked` or `[open]`; (3) the CSS is complete (no string or comment left open) and comes from the document itself, not from a style sheet file; (4) the browser parses both texts to the same document; (5) both texts are laid out identically, box by box and text by text, in a hidden copy of the page pane; (6) no part that is hidden at the moment (hidden attribute, closed `details`) contains block elements displayed inline or generated content, because such a part has no boxes to compare. Otherwise the source stays as it is and a message says why. If the text changes while the check runs, the result is dropped.

### What stays untouched

* A visual edit rewrites only the edited part of the body content. Doctype (including public and system identifiers), `html`/`head`/`body` tags, head content, comments, attributes, character references, quoting style, upper-case tags, scripts and event handlers stay exactly as written.
* Normalizations after a visual edit, all limited to the edited place:
  * edited text is written with `&amp;`, `&lt;`, `&gt;`, `&nbsp;`; unchanged text before and after the edit in the same text run keeps its original spelling;
  * an element whose end tag was omitted gets an end tag only if the element directly after it changed;
  * a paragraph renamed to a heading (or back) keeps its attributes verbatim;
  * changing an image or a link through its dialog, and aligning a block, rewrite exactly the attribute concerned inside the start tag: its value is replaced within the quotes the pupil used, a missing attribute is added behind the last one, a removed one goes with the white space in front of it; the tag name, the other attributes, their order, spelling and spacing stay. In a badly written tag the result follows what the browser reads: if a name occurs several times, a new value goes to the first occurrence (the one that counts) and a removal takes all of them; a name followed by an equals sign without a value is treated as an attribute with an empty value;
  * list commands keep attributes as written: a paragraph or heading that becomes a list item passes its start tag to the item, and an item that becomes a paragraph passes it back; an item that holds blocks and has attributes becomes a `<div>` with them; a list with attributes whose items all become paragraphs stays as a `<div>` around them; if items remain, the original list element keeps them, and items behind a paragraph taken out of the middle continue in a second list with the same attributes except `id` and attributes the editor does not show (event handlers);
  * a block created or moved by a list command stands on its own line; a line break between two paragraphs that become neighbouring items is removed;
  * text typed directly into the body is wrapped in `<p>`;
  * trailing spaces inside an edited paragraph may be dropped by the browser;
  * white space that the browser tidies away in a text the pupil did not edit is kept as written: line breaks and indentation between elements always; a space at the edge of a neighbouring text, or a single space between two elements, if it could not be seen (another space or the edge of the block stands next to it) and the pending input consisted of typing only. After a deletion such a space counts as deleted. Firefox tidies in this way while typing;
  * a single line break that the browser itself keeps in a page without visible content (Firefox) is not written into the document.
* Parts of a document that the editor cannot map safely to the source (wrongly nested or unclosed elements, very deep nesting) are shown read-only with a dashed outline. If the body as a whole cannot be mapped, the page is shown read-only and a note asks the pupil to fix the code on the left. The source can always be edited.

### Inactive content

* In the page pane, scripts and event handlers do not run, links do not navigate, forms do not submit, frames, objects, audio and video are replaced by a labelled box, and nothing is loaded from the network or from neighbouring files. Images are shown if they are embedded in the code (`data:` address of a raster format) or if the pupil has chosen the file in this session; other images appear as a dashed box with their description.
* A note above the page says what is switched off ("Im Editor ausgeschaltet: 2 Skripte, 1 Bild von außerhalb, 1 Animation …"). SVG animation elements are not shown, because an animation can assign an address after the attributes were filtered. If the browser's content policy stops something that the editor's own list did not name, the note says "Inhalte von außerhalb der Seite (vom Browser blockiert)". This part of the note stays until another document is opened or created, also if the pupil removes the cause: the editor cannot tell which text caused the stop. The source and the saved file keep all of it. The editor does not claim that a saved document is safe to open elsewhere.

### Files

* Open: file picker of the browser, or a plain file input where the picker API is missing. UTF-8 with or without byte order mark. A file that is not valid UTF-8 is opened only after a question, converted from Windows-1252, and then counts as unsaved without a target file. UTF-16 and binary files are refused. Limit: 5 MB.
* Line ends: the editor works with LF internally. A file with CRLF line ends is written back with CRLF, a byte order mark is written back. A file opened and saved without edits is byte-identical. Mixed line ends are unified to the dominant convention and this is announced.
* Save writes to the opened file (after the browser's permission question) or asks for a location. Where the browser has no file access API, or it fails, Save downloads the file instead. "Herunterladen" always downloads a copy.
* A document is marked as saved only after a completed write or a started download. A cancelled or failed save leaves it unsaved and says so. A started download counts as saved; the editor cannot see whether the browser's download was kept.
* New, Open and dropping a file ask before unsaved work is discarded. The answer covers the document as it was at that moment: if the text changes while a file is being chosen or read, the editor asks again before it replaces anything, and declining keeps the work and its undo history. Of several such operations only the one started last can complete; an older file read that finishes later is dropped with a message. Closing the tab with unsaved work triggers the browser's warning. Nothing is stored between sessions.

### Limits

| Limit | Value |
| --- | --- |
| Opened file | 5 MB |
| Image file | 20 MB; a file above 2 MB is pointed out in the dialog |
| Image width | 1 to 9999 pixels |
| Pasted text | 200,000 characters |
| Syntax colours | switched off above 1.5 million characters; lines above 4,000 characters are shown without colours |
| History | 300 steps or 40 million characters |
| Nesting depth that stays editable | 400 levels |

## 2. Known limitations of version 0.1.0-alpha.5

* The page pane always renders in standards mode, also for documents without a doctype.
* Images referenced by file name are shown only after the pupil has chosen the file in the current session, so after reopening a page they are boxes until chosen again. The editor cannot check that the file really lies where the address says, and it does not copy the file there. A function that opens a whole folder would lift this; it is not part of this version.
* A picture is placed by the alignment of its paragraph. Text does not flow around pictures unless the pupil writes CSS for it.
* External style sheets are not applied in the editor; `<style>` in the document is. Documents with an external style sheet cannot be formatted with "Code aufräumen".
* "Code aufräumen" answers for the page as its own CSS describes it. A script of the page that changes styles or classes later, and a part that a rule of its own hides completely (`display: none`) and something else shows again, are outside what the checks can see. Pages with rules that hold only sometimes are refused as a whole, also when the rule would do no harm.
* SVG animations are not shown in the editor.
* `<form>` is displayed as a plain block; form controls are not operable in the editor.
* Nested lists are created in the source, not with the toolbar.
* Typing at the end of a link continues the link (browser behaviour).

## 3. Origin

A third-party single-file HTML editor served as a reference for interaction concepts. It is referred to as `[REFERENCE-APP]` (its accompanying notes as `[REFERENCE-NOTES]`); identity, revision and hashes are kept in a private analysis case and are not published. No general licence for reuse was found for it. Its source was read to understand how it works. This folder contains no code, assets, templates or texts of it; all files here were written for this project. No formal clean-room process is claimed: the author of this code has seen the reference source.

Source ranges of `[REFERENCE-APP]` that were read for this work: lines 555–604 (layout) and 622–1219 (state, highlighter, preview rendering, write-back, selection mapping, toolbar, file handling, formatter). The parts on templates, minification, validation and autosave (after line 1219) were not re-read; statements about them rely on the earlier audit findings RF-08, RF-11, RF-12 and RF-14.
